# FLAC & Image Codecs (S32)

> Target spec + honest delta for the pure-TS FLAC codec and the still/animated image family.
> Owned code: `src/codecs/flac/decode.ts`, `src/codecs/flac/encode.ts`, `src/codecs/image/{decode,image-driver,index,probe}.ts`.
> This document describes the **best** design and an explicit punch-list versus today's code — not merely what exists.

## 1. Purpose & scope

This shard covers two small, self-contained codec families that share one property: they are **integer / self-describing bitstreams**, so their pure-TS tier is provably correct without a browser or a WASM toolchain.

- **FLAC** — a lossless, integer audio codec. A pure-TS decoder (`src/codecs/flac/decode.ts`) turns a native `fLaC` stream into per-channel `Int32Array` PCM plus the STREAMINFO MD5; a pure-TS encoder (`src/codecs/flac/encode.ts`) authors a genuinely-compressing native FLAC stream (FIXED predictor + partitioned Rice + stereo decorrelation, VERBATIM floor). Both are **bit-exact**: the encoder's residual arithmetic is the exact inverse of the decoder's, and STREAMINFO's PCM MD5 is a self-validation oracle a real `flac`/`ffmpeg` decoder can independently reproduce (`decode.ts:1-11`, `encode.ts:1-14`, ADR-024/ADR-086, `measured-evidence.md`).
- **Images** — still/animated **GIF / PNG (+APNG) / JPEG / WebP / AVIF**. Two capabilities split by validation tier (`index.ts:3-15`, ADR-025): a **pure-TS header probe** (`src/codecs/image/probe.ts`, Node-validated, bit-exact on real files) and a **browser-only pixel decode** via the WebCodecs `ImageDecoder` (`src/codecs/image/decode.ts`, capability-gated).

**Benchmark families served.** `decode` and `probe` (per `docs/architecture/COVERAGE.md`). Concretely:
- FLAC feeds `probe` and `demux` (frame-span enumeration via `enumerateFlacFrameSpans`, `decode.ts:371`), and the audio decode/transcode/trim/mux paths owned by other shards (S12/S14/S16/S28) consume this codec. FLAC decode is also the shipped fallback where the browser has no FLAC `AudioDecoder` (Chrome 149 has none — `measured-evidence.md`, ADR-024).
- Images serve `probe` (bit-exact header oracle) and `decode` (pixel path). Images are registered as an **`ImageOps` side capability**, *not* a `ContainerDriver`/`CodecDriver`, because they have no per-track packet seam and no `DecoderConfig` handoff (ADR-049, `index.ts:9-14`, `image-driver.ts:1-16`).

Out of scope here: the FLAC *container* driver and Ogg/MKV muxing (S28/S26/S14), the WAV→FLAC verbatim fast path (S12), and the image→engine wiring in `defaults.ts`/`engine.ts` (S04/S05). This shard owns only the two codec cores.

## 2. Spec & references

**FLAC.**
- Governing standard: **RFC 9639 — Free Lossless Audio Codec (FLAC)** (IETF, 2024). <https://www.rfc-editor.org/rfc/rfc9639.html>. The code cites it by section throughout: STREAMINFO, subframe types §9.2, FIXED predictor §9.2.6, partitioned Rice §9.2.7 (`encode.ts:46-57`, `decode.ts:121-204`).
- STREAMINFO MD5: computed per **RFC 1321 (The MD5 Message-Digest Algorithm)**. <https://www.rfc-editor.org/rfc/rfc1321>. The streaming MD5 core lives in `encode.ts:1028-1201`.
- OSS exemplar: **libFLAC (xiph/flac)** — `src/libFLAC/stream_decoder.c` <https://github.com/xiph/flac/blob/master/src/libFLAC/stream_decoder.c> and `src/libFLAC/stream_encoder.c` <https://github.com/xiph/flac/blob/master/src/libFLAC/stream_encoder.c>. Reference for: the fixed-blocksize STREAMINFO min==max convention (`encode.ts:206-235`), the sum-of-|residual| FIXED-order heuristic (`encode.ts:506-529`), and partition-order search (`encode.ts:631-675`). Our encoder is FIXED-only where libFLAC also does LPC — see Delta §5.7.

**Images.**
- Pixel decode: **W3C WebCodecs — `ImageDecoder` interface**. <https://www.w3.org/TR/webcodecs/#imagedecoder-interface> and the **WebCodecs Codec Registry** <https://www.w3.org/TR/webcodecs-codec-registry/>. Platform reference: MDN `ImageDecoder` <https://developer.mozilla.org/en-US/docs/Web/API/ImageDecoder> — the named "platform ImageDecoder" exemplar. Used in `decode.ts:85-114`.
- Header parsing standards (probe):
  - **PNG (Third Edition, incl. APNG)** — W3C/ISO/IEC 15948. <https://www.w3.org/TR/png-3/> (IHDR, `acTL`/`fcTL`; `probe.ts:284-353`).
  - **JPEG** — ITU-T T.81 / ISO/IEC 10918-1 <https://www.w3.org/Graphics/JPEG/itu-t81.pdf>; JFIF ITU-T T.871 <https://www.itu.int/rec/T-REC-T.871>. (SOFn walk; `probe.ts:355-413`.)
  - **GIF89a** — CompuServe Graphics Interchange Format. <https://www.w3.org/Graphics/GIF/spec-gif89a.txt> (Image Descriptor, Graphic Control Extension, NETSCAPE2.0 loop; `probe.ts:198-282`).
  - **WebP** — RIFF container spec. <https://developers.google.com/speed/webp/docs/riff_container> (`VP8 `/`VP8L`/`VP8X`, `ANIM`/`ANMF`; `probe.ts:415-520`).
  - **AVIF** — AV1 Image File Format. <https://aomediacodec.github.io/av1-avif/> built on **ISO/IEC 23008-12 (HEIF)** and **ISO/IEC 14496-12 (ISO-BMFF)**. (`ftyp` brand, `ispe`, `av1C`, `stsz`; `probe.ts:522-629`.)

## 3. Target design

### 3.1 Data model & seams

**FLAC.** Two flat, allocation-transparent shapes and one streaming class:
- `FlacDecoded` — `{ sampleRate, channels, bitsPerSample, totalSamples, samples: Int32Array[], md5 }` (`decode.ts:16-24`). `samples` is planar signed PCM at the stream's native depth; `md5` is the STREAMINFO digest (the oracle).
- `FlacPcm` — the encoder's read-only planar input (`encode.ts:20-26`), buildable zero-copy from `FlacDecoded` (`flacPcmFromDecoded`, `encode.ts:60-68`) or quantized from canonical `PcmAudio` (`flacPcmFromPcmAudio`, `encode.ts:75-97`).
- `FlacFrameSpan` — a **byte-exact** native-frame locator `{ offset, size, samples, ptsSamples, ptsUs, durationUs, data }` (`decode.ts:27-42`), the demux/remux/trim seam: every FLAC frame is independently decodable (intra), so a span is a keyframe boundary.
- `FlacFrameEncoder` — the streaming authoring seam: one planar block → one native frame, accumulating min/max block+frame sizes so `finalizeStreamInfo(md5)` can emit a complete STREAMINFO once the stream ends (`encode.ts:165-236`). `streamInfoPrelude(config)` emits a valid `fLaC`+STREAMINFO header with the spec's "unknown" zeros for total-samples/MD5, which the muxer backfills (`encode.ts:826-836`).

**Images.** One structured header result and one capability object:
- `ImageInfo` — `{ format, width, height, frameCount, animated, bitDepth, colorType, loopCount?, durationSec? }` (`probe.ts:43-61`). `loopCount: Infinity` = loop forever; `durationSec` present only when the header carries per-frame delays (GIF/APNG/WebP). `imageInfoToMediaMetadata` maps this to the engine's one-video-track probe shape (`probe.ts:81-104`).
- `ImageOps` — `{ formats, sniff, probe, canDecode, decode, decodeFrames }` (`image-driver.ts:34-50`), the single side-capability surface a host holds and routes to when a source sniffs as an image. The singleton `imageOps` is stateless, so one shared instance is safe (`image-driver.ts:52-60`).

The image seam is deliberately **not** a driver kind (ADR-049): `ImageDecoder` consumes the whole encoded buffer, so there is no demux-to-`EncodedChunk` step to model. `registerImageSupport(reg)` attaches the ops only onto a host that exposes `addImageOps` (`image-driver.ts:81-99`).

### 3.2 Capability routing (WebCodecs → GPU → WASM, miss-only)

This family is where the routing philosophy has two principled *exceptions*, and the doc must be explicit about both:

- **FLAC decode.** Target ladder: WebCodecs `AudioDecoder('flac')` (hardware/native) → **miss ⇒ the pure-TS decoder in this shard** — *not* WASM (ADR-024, `measured-evidence.md`). FLAC is a lossless integer codec, so a pure-TS decoder is bit-exact and only kilobytes; shipping WASM here would add megabytes for no correctness gain. Chrome 149 ships **no** FLAC `AudioDecoder`, so in practice the pure-TS tier is the live path on Chromium (`measured-evidence.md`). Whether the router *attempts* WebCodecs FLAC first is owned by S01/S13; this shard supplies the always-correct fallback.
- **FLAC encode.** No WebCodecs FLAC encoder exists in any browser, so the pure-TS encoder here is the **only** authoring path (ADR-086). (A competitive-gaps note calling FLAC encode "missing" is stale — the encoder exists and `transcode/wav_to_flac` ships green; see `measured-evidence.md` line 22 vs line 537, Open Question §6.)
- **Image decode.** Target ladder: WebCodecs `ImageDecoder` (browser-native, hardware-assisted) → **miss ⇒ a typed `CapabilityError`** (`decode.ts:38-48`, `decode.ts:75`). There is deliberately **no GPU or WASM software fallback**: images have no honest bit-exact software decoder in-tree, so `force-software` and Node both return a typed miss rather than fabricate pixels (ADR-018/ADR-025; `measured-evidence.md` — image decline reads at most the 4 KiB routed prefix; the engine-side decline lives in `engine.ts:1179-1187`). `hasImageDecoder()` (`decode.ts:34-36`) is the honest capability probe.
- **Probe (both).** Pure-TS, always available (Node tier), no routing and no download. The un-fakeable oracle is "frame count + dimensions + header timing match the real file" (`probe.ts:1-18`; FLAC STREAMINFO MD5 for the audio side).

The developer never names a backend: they call `probe`/`decode`; routing is internal, and a true miss is a loud typed `CapabilityError` carrying `{ op, tried, suggestion }` (`errors.ts:36-55`, `decode.ts:39-47`).

### 3.3 Edge cases

- **B-frames.** *Not applicable.* FLAC is audio (no picture reordering); images have no inter-frame prediction. Every FLAC frame and every image frame is independently coded.
- **VFR (variable frame rate).** *Applies to animated images only.* GIF/APNG/WebP carry **per-frame** delays; the probe sums the exact header delays into `durationSec` (GIF centiseconds `probe.ts:251-253,270`; APNG `delay_num/delay_den` `probe.ts:333-336`; WebP `ANMF` ms `probe.ts:481-484`), and decode stamps each frame from its own `VideoFrame.duration`, accumulated into a monotonic `timestamp` (`decode.ts:102-110`). Where a frame omits a duration, a 100 ms GIF default keeps timestamps advancing (`decode.ts:24-25,104`). FLAC's analog is *variable block size*; the encoder emits a **fixed-blocksize** stream (min==max in STREAMINFO) so libFLAC does not warn on seek (`encode.ts:206-235`).
- **Seek.** FLAC: every native frame is a keyframe; `enumerateFlacFrameSpans` gives byte-exact per-frame spans with PTS for the container/trim layer to seek on (`decode.ts:371-390`). Frame sync bytes (`0xff`) can appear inside payload, so frame selection must CRC-check headers, not scan for `0xff` (`measured-evidence.md`, ADR-096). Images: `ImageDecoder.decode({frameIndex})` is random-access, but the current generator only decodes sequentially — see Delta §5.8.
- **Cancel.** Images: full `AbortSignal` support — `throwIfAborted` between steps and `raceAbort` around `tracks.ready`/`decode` (`decode.ts:81,89,96-100,168-190`); an abort runs the generator's `finally` which closes the decoder. FLAC: whole-buffer synchronous CPU work; not cancellable mid-decode (acceptable for the Node tier, but see Delta §5.5 for longform bounding).
- **Frame lifetime (`close()` exactly once).** FLAC produces `Int32Array` planes, **not** `VideoFrame`/`AudioData` — so "close exactly once" does not apply at this layer; the DSP/driver consumer builds `AudioData`. Images: the contract is **the consumer owns each yielded `VideoFrame` and `close()`s it exactly once** (`decode.ts:9-14,64-70`). `restamp` closes the original when it wraps for corrected timing so exactly one handle survives (`decode.ts:160-165`); the generator's `finally` closes the `ImageDecoder` on every exit (done/throw/abort) (`decode.ts:112-114`); `ReadableStream.cancel` calls `iterator.return()` to trigger that `finally` (`decode.ts:142-146`). Two residual leak windows are called out in Delta §5.4 and §5.9.
- **Backpressure.** Images: the generator is pull-driven (decode frame N only on demand), and the `ReadableStream` wrapper uses `highWaterMark: 0`, so at most one decoded frame is alive — no GPU-memory pile-up (`decode.ts:16-19,124-149`). FLAC decode is whole-buffer (no streaming backpressure); the streaming *encoder* is block-push, so the caller paces it.

## 4. Current state

**`src/codecs/flac/decode.ts` (408 lines).** A complete pure-TS decoder: MSB-first `BitReader` (`decode.ts:45-96`); STREAMINFO/metadata walk with ID3v2 skip (`readStreamInfo`, `decode.ts:267-305`); per-frame decode incl. UTF-8 frame-number skip, block-size/sample-rate/BPS tables, subframe decode for CONSTANT/VERBATIM/FIXED(0-4)/**LPC(1-32)**, partitioned Rice with 4/5-bit params + escape, and L/S·R/S·M/S decorrelation (`decode.ts:98-343`). `decodeFlac` (`decode.ts:346-368`) and `enumerateFlacFrameSpans` (`decode.ts:371-390`) are the public entry points; `interleavedPcmBytes` (`decode.ts:393-407`) serializes PCM in STREAMINFO-MD5 order. Smells:
  - **Public hot-loop helpers.** `at()` and `chan()` (`decode.ts:110-119`) — bounds-checked element/channel reads — are `export`ed purely so a unit test can hit both arms (`decode.test.ts:49-58`). Internal predictor scaffolding leaks into the module's export surface.
  - **`interleavedPcmBytes` duplicated.** Defined here (`decode.ts:393`) and again in `encode.ts:848`, with slightly different byte extraction (`v >>= 8` vs `Math.floor(value/256)`). Two copies of the MD5-serialization contract.
  - **Whole-stream allocation.** `decodeFlac` allocates `Int32Array(totalSamples)` per channel up front (`decode.ts:347-348`); `enumerateFlacFrameSpans` fully *decodes* every subframe just to measure byte spans (`decode.ts:371-388`).
  - **Documented exactness ceiling.** The header comment concedes the predictor sum is exact "for the ≤24-bit content real files use" (`decode.ts:8-11`); `restoreLpc` accumulates in a JS `number` (`decode.ts:166-171`), and the LPC shift is read as *signed* 5-bit (`decode.ts:194`) with no ≥0 guard.

**`src/codecs/flac/encode.ts` (1202 lines) — the god-file of this shard.** It fuses five concerns that ideally live apart: PCM quantization/validation (`encode.ts:75-97,256-336`), cost-only subframe planning + partitioned-Rice search (`encode.ts:349-720`), a growable MSB-first `BitWriter` with bulk Rice emission (`encode.ts:864-967`), frame-header/STREAMINFO serialization + CRC-8/CRC-16 (`encode.ts:737-1008`), and a full streaming **MD5** implementation (`encode.ts:1028-1201`). Module-global mutable scratch: `MD5_WORDS` is a shared `Uint32Array(16)` reused across `md5Block` calls (`encode.ts:1066,1069-1078`) — fine single-threaded, but a hidden shared buffer. The encoder is FIXED-only (no LPC) by design (`encode.ts:46-47`, ADR-086).

**`src/codecs/image/probe.ts` (668 lines).** From-scratch, bounds-checked header parsers for all five formats with typed-`InputError` truncation guards (`probe.ts:106-156`), magic-byte sniff (`sniffImageFormat`, `probe.ts:166-175`), and a public dispatch (`probeImage`, `probe.ts:639-661`). Each parser is well-isolated; the AVIF box walk recurses containers (`probe.ts:574-629`). Boundary honesty is uneven: WebP always reports `bitDepth: 8` (`probe.ts:440,451,497,503`) while PNG/JPEG/AVIF read real depth — see Delta §5.10.

**`src/codecs/image/decode.ts` (193 lines).** The browser pixel path: `hasImageDecoder` gate (`decode.ts:34-36`), typed-miss factory (`decode.ts:38-48`), `inspectImage` (`decode.ts:55-62`), the `decodeImageFrames` async generator (`decode.ts:71-116`) and `decodeImage` `ReadableStream` wrapper (`decode.ts:124-151`), plus `restamp`/`throwIfAborted`/`raceAbort` helpers (`decode.ts:160-190`). Everything past the `hasImageDecoder()` guard is `/* v8 ignore */`-marked browser-only and harness-validated; the Node-reachable gates are unit-tested (`decode.test.ts`).

**`src/codecs/image/image-driver.ts` (102 lines) + `index.ts` (47 lines).** The registration hook and public barrel. **Layering smell (confirmed):** the docstring claims `register` is "a no-op against the plain driver `Registry` (it has no image slot)" (`image-driver.ts:9-15,78-99`) — but this is **stale**. The kernel `Registry` now *implements* `ImageRegistry` and imports `ImageOps`/`ImageRegistry` *from this codec file* (`src/kernel/registry.ts:11,27,45,63-64,79-80`). So the generic kernel depends on the codecs layer, and `defaults.ts:96` still defensively casts `reg` to an optional `addImageOps?` even though the slot is now mandatory. This is a capability leak: a codec-layer type is the kernel's dependency.

## 5. Delta / punch-list

Ordered; each item names the change, the `path:line`, and a concrete acceptance oracle.

1. **Hoist the `ImageOps`/`ImageRegistry` contract out of the codecs layer; fix the stale docstring.** Today `src/kernel/registry.ts:11` imports these types from `src/codecs/image/image-driver.ts`, and `Registry` implements `ImageRegistry` (`registry.ts:45`), so the kernel depends on a codec module. Move the `ImageOps`/`ImageRegistry` *interfaces* into the driver-contracts layer (S04, `src/contracts/`), have `image-driver.ts:34-50,63-65` import them, and rewrite the `image-driver.ts:9-15,78-99` docstring to reflect that the kernel `Registry` *does* own an image slot. **Acceptance:** `grep -r "codecs/image" src/kernel` returns nothing; `registry.test.ts` (addImageOps idempotency) stays green; `defaults.ts:96` drops the optional `addImageOps?` cast and calls the now-mandatory slot directly.

2. **Make the LPC predictor bit-exact for full 32-bit streams.** `restoreLpc` sums `coef*sample` in a float64 (`decode.ts:166-171`); a 15-bit coefficient × 33-bit side-channel sample over up to 32 taps can exceed 2^53 and silently lose bits — the code's own comment admits exactness only "for ≤24-bit content" (`decode.ts:8-11`). Accumulate in a mantissa-safe way (BigInt for the wide case, or a split hi/lo accumulator) so the predictor is exact for `bitsPerSample === 32`. **Acceptance:** add a 32-bit / high-order-LPC FLAC fixture (or synthesize one) and assert `md5(interleavedPcmBytes(decodeFlac(bytes))) === hex(md5)` (the same STREAMINFO-MD5 oracle as `decode.test.ts:20-25`); a deliberately overflow-inducing crafted subframe must decode bit-exactly, not drift.

3. **Reject an illegal negative LPC shift with a typed error.** `restoreLpc` reads the quantization shift as signed 5-bit (`decode.ts:194`) and applies `Math.floor(sum / 2**shift)` (`decode.ts:169`); RFC 9639 §9.2.8 requires shift ≥ 0, and a negative value would silently mis-scale (turning a right shift into a left shift) instead of rejecting a malformed/fuzzed stream. Throw `MediaError('decode-error', ...)` when `shift < 0`. **Acceptance:** a crafted subframe with a negative shift raises `MediaError` (mirror the lost-frame-sync test at `decode.test.ts:39-46`); the IETF corpus still passes MD5 (`decode.test.ts:19-26`).

4. **Close the in-flight `decoder.decode()` frame on abort.** `raceAbort` (`decode.ts:173-190`) rejects as soon as the signal aborts, abandoning the underlying `decoder.decode()` promise; if that promise later resolves to `{ image }`, the `VideoFrame` is never `close()`d (the `finally`'s `decoder.close()` at `decode.ts:113` may not release an already-vended frame). Attach a continuation that `close()`s any late-resolving image. **Acceptance (browser/fake-`ImageDecoder` harness):** abort mid-decode with a stub whose `decode()` resolves *after* the abort; assert the late `VideoFrame.close()` is called exactly once and no frame leaks (track live-frame count).

5. **Add a bounded/streaming FLAC decode for longform decode-seek/trim.** `decodeFlac` allocates the whole PCM up front (`decode.ts:347-348`), so a one-hour 96 kHz file materializes hundreds of MB. Add a generator that yields one decoded frame's planes at a time (bounded to O(blockSize·channels)), reusing `decodeFrame` (`decode.ts:307-343`). **Acceptance:** decoding a synthesized long FLAC keeps peak allocation O(blockSize·channels), not O(totalSamples), measured by a heap/`ArrayBuffer`-peak probe (cf. the WAV memory-lifecycle method in `measured-evidence.md`); per-frame MD5 accumulation still reproduces the STREAMINFO digest.

6. **Split frame-span enumeration from frame decoding.** `enumerateFlacFrameSpans` fully decodes every subframe just to measure byte spans (`decode.ts:371-388`) — correct for goldens, wasteful for the demux/`packetInfo` hot path. Keep the decode-validating enumerator (rename it `enumerateFlacFrameSpansValidating` for `test-support/packet-goldens.ts`) and add a header-only walk that parses + CRC-checks the frame header and re-syncs to the next `0x3ffe`/CRC-valid boundary without decoding PCM. **Acceptance:** the header-only walk on `flac-blocksize-16.flac` yields byte-identical spans to the validating enumerator (harvest: 19,294 packets) with no subframe decode; a benchmark shows it at the fused-parser scale (~10^-3 ms, `measured-evidence.md`), not the decode-bound cost.

7. **Add LPC subframes to the encoder (compression-ratio ceiling).** The encoder is FIXED-only (`encode.ts:46-47,479-495`); ADR-086 flags LPC as the future ratio win, and the decoder already restores LPC (`decode.ts:159-171`). Add Levinson-Durbin windowed LPC analysis, quantized coefficients, and a `writeSubframe` LPC arm, keeping the cost-only planning model (`encode.ts:349-495`). **Acceptance:** on the `wav_s16` corpus the compressed size beats the FIXED-only baseline while `decodeFlac`→STREAMINFO-MD5 still round-trips bit-exactly (`encode.test.ts`), and an independent `flac -t`/`ffmpeg` decode confirms the output.

8. **Expose random-access frame seek for animated images.** `decodeImageFrames` always iterates `0..frameCount` (`decode.ts:95-111`) even though `ImageDecoder.decode({frameIndex})` is random-access (`decode.ts:97-100`). Accept an optional `{ startIndex, endIndex }` in `DecodeImageOptions` (`decode.ts:28-31`) so a seek decodes only the requested range with correct cumulative timestamps. **Acceptance (browser harness):** decoding frame 20 of a 36-frame GIF issues exactly one `decode({frameIndex:20})` and returns a frame whose `timestamp` equals the summed prior header delays; zero prior frames decoded.

9. **Close any queued `VideoFrame` when the `ReadableStream` is cancelled.** `decodeImage`'s `pull` transfers ownership via `controller.enqueue(value)` (`decode.ts:137`); with `highWaterMark: 0` this is normally demand-paced, but a `cancel()` that races a resolved-but-unread enqueue would drop that `VideoFrame` without `close()`. Add a queuing strategy / cancel hook that drains and closes any queued frame. **Acceptance:** cancel immediately after a `read()` resolves with a fake decoder that had a frame queued; assert no leaked frame (live-frame count returns to zero). If proven unreachable under HWM 0, replace the fix with a test that *documents* the invariant.

10. **Pin the `bitDepth`/`colorType` exactness boundary per format.** WebP unconditionally reports `bitDepth: 8` (`probe.ts:440,451,497,503`) and `colorType` is a fixed `'lossy'`/`'lossless'`/`'rgb'`/`'rgba'` guess, whereas PNG (`probe.ts:326-327`), JPEG precision (`probe.ts:397,407`), GIF GCT depth (`probe.ts:215`), and AVIF `av1C` (`probe.ts:617-621`) read real header values. Document, per format, which fields are exact vs assumed, and assert the exact ones. **Acceptance:** a per-format probe test asserts `bitDepth` against ffprobe/real-file truth for ≥1 fixture each; formats where depth is assumed (WebP) carry an explicit `UNVERIFIED`-style code comment and an open decision (§6).

11. **Stop exporting the `at()`/`chan()` hot-loop helpers; dedup `interleavedPcmBytes`.** `at`/`chan` are `export`ed only for a coverage test (`decode.ts:110-119`, `decode.test.ts:49-58`), and `interleavedPcmBytes` exists twice (`decode.ts:393`, `encode.ts:848`). Make `at`/`chan` module-private (exercise both arms via a crafted corpus fixture through `decodeFlac`) and keep a single `interleavedPcmBytes` (one shared helper, imported by both). **Acceptance:** `grep "export function at\|export function chan" src/codecs/flac/decode.ts` is empty; only one `interleavedPcmBytes` definition remains; branch coverage stays ≥ the repo gate and all MD5 round-trip tests pass.

## 6. Open questions

1. **Is FLAC encode advertised as available, or a hard miss?** `measured-evidence.md` line 22 (ADR-086) and line 403 say the pure-TS encoder exists and ships (`transcode/wav_to_flac` green), but line 537 (competitive-gaps) calls FLAC encode "entirely missing / an unconditional hard miss." The code (`encode.ts`, wired via `flac-driver.ts`/`flac-codec.ts`) proves the encoder exists. Log a decision reaffirming FLAC encode = pure-TS (the only path) and retire the stale competitive-gaps line.
2. **32-bit / negative-shift bit-exactness scope (Delta §5.2/§5.3).** Do we commit to full 32-bit LPC exactness and strict shift validation, or formally scope the decoder to ≤24-bit (rejecting 32-bit LPC with a typed `CapabilityError`)? Decide and encode the boundary in the STREAMINFO-parse guard.
3. **Software image-decode tier.** Image decode is a hard `CapabilityError` in Node/force-software (`decode.ts:38-48`, `engine.ts:1179-1187`, ADR-018). Do we ever ship a bit-exact software still-image decoder (e.g., a pure-TS PNG/BMP path) so `force-software` image work is honest, or keep it a permanent typed miss? Log the trade-off (bundle cost vs honesty).
4. **`ImageOps` contract ownership (Delta §5.1).** Confirm the `ImageOps`/`ImageRegistry` interfaces move to `src/contracts/` and that images remain a *side capability* (ADR-049) rather than being promoted to a fourth driver kind — record the layering rule so the kernel never re-imports a codec type.
5. **Probe `bitDepth`/`colorType` completeness (Delta §5.10).** Decide the guaranteed-exact subset of `ImageInfo` fields (dimensions, frame count, header duration are exact oracles today) versus best-effort fields (WebP depth), and whether best-effort fields belong in the public probe shape at all.
